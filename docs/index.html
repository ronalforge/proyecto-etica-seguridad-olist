1. Resumen ejecutivo

Este proyecto construye un prototipo académico para analizar las entregas tardías de un conjunto histórico de comercio electrónico de Olist. La necesidad de negocio es identificar segmentos que ameriten una investigación logística y mostrar la relación descriptiva entre el cumplimiento de la fecha estimada y la calificación de la compra. El profesor autorizó el dataset base. Se incorpora un segundo conjunto de datos, el calendario oficial de feriados nacionales de Brasil para 2018.

La importación seleccionó 96 470 pedidos entregados con fechas y estado del cliente disponibles, de 99 441 pedidos del archivo original. De ellos, 6 534 llegaron después de la fecha estimada: 6.8 %. Entre las entregas tardías, el retraso medio fue de 10.6 días. La calificación promedio con reseña disponible fue de 4.29/5 para las puntuales y 2.27/5 para las tardías.

El prototipo integra una base SQLite cifrada con SQLCipher, backend Flask y panel React con componentes shadcn/ui. Implementa autenticación, roles RBAC (admin, analyst, reader), registro de auditoría, transporte HTTPS local y respaldos autenticados con AES-256-GCM.

2. Introducción y caso de negocio

2.1 Problema y oportunidad

En una operación de comercio electrónico, conocer solo el número total de pedidos no permite priorizar la revisión de demoras. Un indicador global puede ocultar diferencias entre estados o meses, mientras que una lista de pedidos individuales expondría datos que el analista no necesita. Se plantea una vista agregada que permita responder: ¿cuál fue la tasa de tardanza?, ¿en qué grupos históricos fue mayor?, y ¿cómo varió la calificación observada entre pedidos puntuales y tardíos?

2.2 Objetivos

  • Integrar el dataset Olist con una fuente complementaria verificable de feriados (Portaria n.º 468/2017).
  • Definir KPIs con denominadores explícitos y explorar variaciones por estado y mes.
  • Implementar una base de datos relacional cifrada, un backend seguro y una interfaz web con control de acceso.
  • Demostrar controles de autenticación, auditoría, transporte HTTPS local y recuperación mediante respaldo cifrado.
  • Documentar riesgos, límites éticos, respuesta a incidentes y lecciones aprendidas.

9. Implementación y evidencias visuales

4 Figuras Clave

Se presentan las evidencias gráficas obtenidas directamente durante la ejecución del prototipo local, organizadas con su correspondiente pie de figura, análisis de lo observado y el requisito formal que acredita según la rúbrica del curso.

1 Panel General: KPIs y Trazabilidad de Fuentes

Qué se observa: Interfaz interactiva desplegada en React tras autenticarse con el usuario administrador (marco · admin). Exhibe los 4 KPIs clave: 6.8 % de entregas tardías, 96 470 pedidos analizados, 10.6 días de retraso promedio y calificaciones de 4.29/5 (puntual) vs. 2.27/5 (tardía), además de la comparación regional y el pie con las fuentes oficiales.

Requisito que demuestra: Requerimientos de Negocio y Funcionales (F1, F2). Generación cuantificable y objetiva de valor logístico a partir de datos históricos, aplicando agregación y minimización sin comprometer la privacidad del cliente.

2 Filtro por Estado: Reactividad y Consistencia Analítica

Qué se observa: El panel tras aplicar el filtro al estado de Maranhão (MA). Los pedidos se reducen a 717, la tasa de tardanza sube al 17.4 % (125 pedidos tardíos), el retraso medio se ajusta a 10.5 días y la satisfacción desciende a 4.17 (a tiempo) y 2.18 (tardío). La serie temporal mensual se adapta exclusivamente a dicho estado.

Requisito que demuestra: Requerimiento Funcional F2 y Diseño Frontend/Backend. Exploración reactiva de segmentos críticos mediante consultas parametrizadas en la API REST (/api/dashboard?state=MA), evitando inyecciones SQL.

3 Auditoría y Control RBAC: Visibilidad Admin vs. Bloqueo 403 Reader

Qué se observa: En el panel (a), la consulta de /audit por el rol admin exhibiendo la traza con fecha UTC, usuario y acciones (login, dashboard_api:MA, etc.). En el panel (b), la denegación estricta con código HTTP 403 Forbidden cuando el usuario lector (rol reader) intenta ingresar a la auditoría.

Requisito que demuestra: Requerimientos de Seguridad en Gestión de Accesos y Auditoría (F4). Aplicación del principio de menor privilegio (RBAC) y trazabilidad inmutable sin exposición de credenciales.

4 Seguridad Técnica: SQLCipher, Respaldo AES-256-GCM y HTTPS TLS 1.3

Qué se observa: Sesión interactiva en terminal comprobando:
1) Cifrado en reposo (SQLCipher): cabecera sin texto plano; el cliente sqlite3 falla arrojando file is not a database (26) y solo abre con la clave de 256 bits recuperando los 96 470 registros.
2) Contingencia y recuperación: respaldo cifrado con AES-256-GCM y restauración comprobada con integrity_check = ok.
3) Transporte HTTPS: negociación TLS 1.3 con suite AEAD-AES256-GCM-SHA384 y certificado ad-hoc.

Requisito que demuestra: Requerimientos Técnicos y de Seguridad: Cifrado en Reposo, Cifrado en Tránsito y Procesos de Recuperación ante Desastres.

11. Lecciones aprendidas y retrospectiva del equipo

11.1 Lecciones técnicas y analíticas

La principal lección técnica es que un dataset público puede contener columnas innecesarias para responder la pregunta de negocio. Definir primero el denominador del KPI permitió importar menos campos y detectar los 646 pedidos sin reseña. En seguridad, restaurar una copia aportó evidencia más contundente que solo generar el archivo cifrado; asimismo, evidenció el límite de custodiar la clave en el mismo equipo.

11.2 Retrospectiva del equipo

  • Llevar un registro estructurado de decisiones arquitectónicas y de seguridad (ADR).
  • Implementar revisión cruzada sistemática de código (peer review) para importadores y controles de acceso.
  • Ejecutar simulacros periódicos de incidentes con la participación de ambos integrantes.

11.3 Declaración sobre el uso de herramientas generativas y plataforma

Todas las decisiones arquitectónicas y de seguridad fueron verificadas y asumidas por el equipo.
